# CHoRUS SOP Website Support Guide

Version 1.0 

## Purpose and scope

This guide explains how to maintain, publish and troubleshoot the CHoRUS standard operating procedure (SOP) website. It is for SOP authors, reviewers and repository maintainers. The repository is the source of truth, changes should be reviewed in a pull request (PR), merged into `main`, built, deployed and checked on the public website.

This guide documents the inspected implementation. Recommendations are labelled separately. Website support does not operate the clinical data pipelines described in the SOPs. Never upload patient data, credentials or restricted materials to this public documentation repository.

## Update or add an SOP

1. **Define the change.** Identify the SOP owner, audience, purpose and supporting sources. Open or reference an issue for a new topic or substantial revision.
2. **Start from current source.** Create a dedicated branch from up-to-date `main`, prefixed with `review`, for example `review-blood-transfusion-update`. If using a fork, open the PR against the upstream repository's `main` branch. Do not overwrite unrelated local changes.
3. **Use the template.** Add the file to the relevant category. Set a unique front-matter `id`, clear `title` and useful `description`; retain established IDs for existing SOPs unless a route change is intentional.
4. **Write actionable content.** Explain purpose, prerequisites, procedure, responsibilities, interpretation and references as needed. Define abbreviations. Replace the template's example version-history link with the history URL for the actual SOP. Remove instructional placeholders.
5. **Handle approval explicitly.** Use `Awaiting Approval` during review. Change it to `Approved` only after the responsible reviewers approve; the template's header is not an automated approval gate.
6. **Check navigation and assets.** Review category placement, image paths, headings, cross-links and the interactive flowchart. Do not assume a filename equals its public URL: Docusaurus document IDs and slugs affect routes. For example, the Blood Transfusion file declares `id: SOP-BTDH`.
7. **Preview and build.** Follow the commands below. Fix errors and review warnings. Inspect wide tables, code blocks, diagrams and mobile layout.
8. **Open the PR.** Describe what changed, why, sources consulted, affected routes, reviewers and test results. Include screenshots for visual changes. Do not say a build passed if it was not run.
9. **Review and merge.** Obtain subject and website review appropriate to the change. An authorized maintainer merges to `main` after acceptance checks.
10. **Verify publication.** Follow both deployment stages and check the live pages. Record the source commit and outcome in the PR.

For small edits through the website, use “Edit this page”, but first inspect the branch and file shown by GitHub. The configured destination is the shared `review` branch. If it is stale or the file is missing, use a fresh dedicated branch from `main` rather than committing unrelated changes to that shared branch.

### Acceptance checklist

- [ ] Correct SOP/category; no accidental edits to unrelated files.
- [ ] Scientific and technical claims reviewed; references and permissions checked.
- [ ] No patient identifiers, secrets, restricted screenshots or private URLs inadvertently published.
- [ ] Front matter parses; ID and intended route are correct.
- [ ] Approval status and version-history link are correct.
- [ ] Build passes; warnings reviewed and documented.
- [ ] Images, tables, code blocks and navigation work in the built preview.
- [ ] Relevant homepage/flowchart links updated and checked.
- [ ] Public deployment and changed routes verified after merge.

## Local preview and build

Use a trusted local checkout, Git and the Node/npm toolchain corresponding to CI. Run these commands from the repository root; they install dependencies and create local generated files, but do not publish:

```bash
cd sop-website
node --version
npm --version
npm install
npm start
```

Open the address printed by Docusaurus. Stop the development server before the production build if needed:

```bash
npm run build
npm run serve
```

Use the address printed by `serve` to check the built site. Development preview alone is insufficient: production builds can fail on MDX syntax, imports or broken links that are not evident while editing. MDX is Markdown with JSX/React support; raw angle brackets or braces may be interpreted as code. Escape them or use inline code when they are literal text.

`npm install` mirrors current CI and may update the lockfile. Inspect the diff and avoid bundling accidental dependency changes with an SOP edit. Do not delete lockfiles or switch package managers just to suppress an error. `npm run clear` can clear Docusaurus-generated cache when investigating stale local output; rebuild afterward.

The nested website README currently calls the framework “Docusaurus 2” and provides Yarn/direct-deploy examples. For this repository's current automated publication path, use the inspected workflow and package configuration above. Do not use `npm run deploy` or the README's direct-deployment commands for routine publishing; they can bypass the reviewed publication process.

## Publish and verify

1. Merge the reviewed PR into `main`.
2. Open Actions and locate `deploy-docusaurus` for the expected source commit. A README-only or workflow-only change does **not** satisfy the configured `sop-website/**` push filter.
3. Inspect `publish` → `Build Docusaurus website`, then `Deploy to GitHub Pages`. Read the first meaningful error, not just the final failure summary.
4. Check the subsequent `pages build and deployment` run. A successful first workflow alone does not establish that the public publication stage completed.
5. Open the homepage, changed SOP URLs and `/flowchart/`; refresh or use a private window to exclude stale browser cache. Confirm the expected content, image loading, direct links and navigation.
6. Record the source SHA, both relevant run links, affected URLs and verification result.

**Manual publication:** an authorized maintainer may select Actions → `deploy-docusaurus` → Run workflow → `main`, after checking which source commit will be published. The workflow supports manual dispatch and does not contain a branch guard restricting dispatch to `main`; selecting another branch can publish that branch's content. Treat dispatch and reruns as real deployments, not harmless tests. Do not rerun an older successful deployment casually: it can republish older content.

## Troubleshooting

| Symptom | Check first | Action |
| --- | --- | --- |
| No workflow after merge | Branch, changed paths and Actions status | Confirm a `main` push touched `sop-website/**`. For an intentional config-only publication, use approved manual dispatch on `main`. |
| Dependency installation fails | Node/npm versions, registry/network error, package and lockfile diff | Reproduce using the workflow's toolchain. Separate dependency repair from content edits. Do not apply forced upgrades blindly. |
| MDX or import build failure | First error with file and line | Check front matter, unmatched JSX, literal braces/angle brackets, import paths and filename case. Rebuild. |
| Broken-link build failure | Reported source page and target | Correct document IDs, slugs, anchors and relative paths. Do not disable link checking to publish. |
| Local preview works but Actions fails | Production build, case-sensitive paths, uncommitted assets | Run `npm run build`, commit required assets and fix case mismatches. |
| Deployment fails after a good build | `Deploy to GitHub Pages` logs and token permission message | Ask an administrator to inspect Actions permissions and `gh-pages` restrictions. Do not create or share a personal token as a shortcut. |
| Pages stage fails | Latest Pages run and its deploy job | Administrator checks Pages source and environment restrictions. Avoid changing settings until the error identifies the cause. |
| Successful runs but old content | Correct source SHA, generated publication commit, browser cache | Confirm both stages correspond to the intended change; verify the direct URL and refresh. |
| Missing sidebar page or wrong order | Front matter, directory/category metadata, route | Check generated navigation and `_category_.json`; keep established IDs stable. |
| Broken image or unstyled page | Path case, base URL, missing committed asset | Use the project's `/Chorus_SOP/` deployment path and inspect the built route. Avoid root-relative paths that omit the project prefix. |
| Flowchart card fails | Hardcoded URL in `InteractiveFlowchart.js` | Compare it with the actual public document/category route; test after update. |
| Edit link is missing or stale | Configured shared `review` branch | Create a fresh branch from `main` and open a PR instead. |

### Incident record

Include the public URL, observed and expected behavior, UTC time, impact, source SHA, run/job links, first useful error, recent changes, reproduction steps, action taken and final verification. Redact logs and screenshots before sharing. Route credentials or patient-data exposure privately to the designated security/privacy owner rather than posting details in a public issue.

## Recovery and rollback

For a content or configuration regression, prefer a reviewed corrective PR or a revert PR against `main`. Preserve the history and document the reason. Reverting a merge requires careful selection of the parent; have a maintainer review it rather than copying a generic merge-revert command.

After the corrective merge, verify both publication stages and the live affected pages. A revert that changes only files outside `sop-website/**` will not automatically trigger this workflow; decide whether manual publication is needed. Do not repair generated HTML directly on `gh-pages`, force-push the repository, or delete deployment history as a routine recovery method.

For a publication failure without a source regression, correct the identified infrastructure or permission problem and rerun only the intended source revision. For a suspected sensitive-data disclosure, stop ordinary publishing and follow the incident process; a revert does not remove information from Git history or caches.

## Maintenance and prioritized improvements

The following are recommendations, not changes already implemented.

| Priority | Improvement | Why and acceptance criterion |
| --- | --- | --- |
| High | Add a non-deploying PR build workflow | Only a deployment workflow was found in `.github/workflows`. PR validation should build changes before merge, without write credentials or publication. |
| High | Define publication permissions and owners | Confirm maintainer/backup, protected branches, Pages source, token scope and security escalation contact. Document the approved settings without recording secrets. |
| High | Guard manual dispatch and serialize publication | Restrict production publication to intended refs; use a reviewed concurrency policy so overlapping deployments cannot unexpectedly publish older output. |
| Medium | Reconcile site URL and editing path | Confirm intended canonical host and check sitemap/canonical URLs; decide whether edit links should target current `main` or a managed review workflow. |
| Medium | Standardize dependency installation | Evaluate `npm ci` with a validated lockfile; choose one package-manager policy. Review Node and third-party Actions support and security before upgrading. |
| Medium | Refresh contributor documentation | Replace the obsolete Docusaurus 2 description and clarify npm/CI publication, path filters and the two deployment stages. |
| Medium | Expand navigation and accessibility checks | Test flowchart targets, external links, keyboard navigation, image alternatives and narrow-screen tables. A build success is not a complete usability check. |

After each publication, perform the release checklist. Monthly, review broken links, active issues/PRs and dependency/security notices. Quarterly, review SOP ownership, approval status, version-history links, restore procedures and support contacts. Adjust this suggested cadence to the team's capacity and risk requirements.
